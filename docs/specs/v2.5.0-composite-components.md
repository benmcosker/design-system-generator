# v2.5.0 — Dialog, Tooltip, Accordion, and Toast

**Status:** specified, not yet implemented
**Scope:** this repo only. Nothing here touches CI/branch-protection infrastructure
(that shipped in v2.1.0) — it's four additions to the generated component set,
using the composite-widget conventions established by Tabs in v2.2.0.

This document is self-contained: it assumes only the current state of
`@benjaminmcosker/design-system-generator` (post v2.4.0, 11 components) and
needs no other context to implement.

**A note on version numbering:** the components originally scoped under an
informal "v2.3.0" label in project discussion were delayed by how
semantic-release actually works — three separate implementation PRs each
triggered their own release (`Tabs` → npm `2.2.0`, `+IconButton` → `2.3.0`,
`+Heading` → `2.4.0`), so `2.3.0` and `2.4.0` are already taken on npm. This
release will land as **v2.5.0** regardless of how many PRs it's split into.

---

## 1. Goal

Extend the generated component library with four composite patterns deferred
from v2.2.0 as "the release after next":

1. **Dialog** (WCAG 2.4.3 Focus Order, 2.1.2 No Keyboard Trap handled
   correctly, 4.1.2 Name/Role/Value) — a modal dialog. None of the 11
   current components trap focus or manage a backdrop; this is the first
   component that removes the user from the normal page flow.
2. **Tooltip** (WCAG 1.4.13 Content on Hover or Focus) — supplementary text
   that appears on hover/focus of a trigger, and must be dismissible,
   hoverable, and persistent per the success criterion. Nothing today
   shows content conditionally on hover.
3. **Accordion** (WCAG 4.1.2, native disclosure semantics) — expandable/
   collapsible sections. Multi-open, built on native `<details>`/`<summary>`.
4. **Toast** (WCAG 4.1.3 Status Messages, 2.2.1 Timing Adjustable) — the
   first **non-presentational** component the generator ships: a
   `ToastProvider` + `useToast()` hook, not a prop-driven component. Every
   one of the 11 existing components is `<Component {...props} />`; Toast
   needs to be triggered imperatively from anywhere in the tree (e.g. after
   a form submit), which the current one-file-per-component export model
   in `renderIndexTs()` doesn't account for.

## 2. What already exists (do not rebuild)

- **Focus visibility (WCAG 2.4.7):** `src/generator/css.ts` puts
  `:focus-visible` rings on every interactive class via one shared
  selector list. All four new components' interactive elements just join
  that list — same mechanism Tabs used in v2.2.0.
- **The multi-test cleanup fix:** `axeTest()` in `src/generator/templates.ts`
  already calls `afterEach(cleanup)` (added in v2.2.0 after Heading/Tabs
  exposed a DOM-leak bug). Any new component with more than one shipped
  `it()` — likely all four here — gets this for free.
- **Tone → role pattern:** `Alert` (`src/generator/templates.ts`, the
  `alertTemplate()` component string) already does
  `const role = tone === 'danger' ? 'alert' : 'status';`. Toast reuses this
  exact logic — a toast is structurally an ephemeral Alert.
- **`IconButton`:** required, non-optional `aria-label`, `icon` prop, reused
  as-is for Dialog's close button and Toast's dismiss button — no new
  icon-button code needed, just consumption.
- **`Heading`:** `level` prop rendering a real `h1`–`h6`. Reused for
  Dialog's title (`level={2}`), wired via `id`/`aria-labelledby` — Dialog
  doesn't need its own heading markup.
- **`aria-live="polite"` pattern:** `TextField`'s error paragraph already
  uses this (`src/generator/templates.ts`, `textFieldTemplate()`). Toast's
  per-toast `role="status"`/`role="alert"` (via the Alert-derived logic
  above) is the composite-widget equivalent — a live region *is* the toast
  itself, not a separate announcer element.
- **Native-first philosophy:** `RadioGroup`, `Switch`, `Select` all lean on
  native elements for keyboard support (see their doc-comments). Accordion
  continues this — native `<details>`/`<summary>` needs no hand-built
  keyboard code at all, unlike Tabs.
- **`ComponentFiles` / `allTemplates()` / `renderIndexTs()`:**
  (`src/generator/templates.ts`, `src/generator/scaffold.ts`) — the
  existing one-function-per-component, append-to-array-and-index pattern.
  Three of four new components fit this exactly. Toast doesn't (see
  Workstream D and §7).

### Corrections to earlier assumptions

**Native `<dialog>`'s `showModal()`/`close()` are not implemented in this
project's jsdom version.** Verified directly against the installed
`jsdom@25.0.1` (the same version pinned in both this repo's own
`package.json` and every generated system's `renderPackageJson()`):
`typeof dialog.showModal === 'undefined'` — calling it throws
`TypeError: dialog.showModal is not a function`. The plain `open`
attribute/property *does* work in jsdom (`dialog.open` reflects
`setAttribute('open', '')` correctly), so **markup and ARIA structure in
the open state can still be axe-tested**, but the actual modal behavior
this component exists for — focus trap, `::backdrop`, focus-return on
close, the native `close` event — **cannot be exercised by this repo's
vitest+jsdom test suite at all**, shipped or otherwise. It can only be
verified in a real browser (manual QA in Storybook; Chromatic here only
does visual-regression screenshots, not interaction testing — there are
no `play` functions anywhere in this codebase today). This is a real,
permanent gap, not a temporary one to "fix later" — document it plainly
in Dialog's test section and its generated `.docs.md` rather than
implying coverage that doesn't exist.

**Toast can't use the existing `ComponentFiles` → `renderIndexTs()` export
pattern unmodified.** `renderIndexTs()` currently hardcodes
`export { ${c.name}, type ${c.name}Props } from ...` for every entry in
`allTemplates()`. Toast exports `ToastProvider`, `useToast`, and
`ToastOptions` — no default-named component/props pair. `ComponentFiles`
needs an optional field (e.g. `indexExports?: string`) that, when present,
overrides the generated export line for that component; every existing
template omits it and keeps today's behavior unchanged.

## 3. Decisions (locked)

| Decision | Choice |
| --- | --- |
| New components this release | `Dialog`, `Tooltip`, `Accordion`, `Toast` |
| Dialog implementation | **Native `<dialog>` element** via `showModal()`/`close()`, exposed through a small imperative handle (`useImperativeHandle`), not a controlled `open` prop. Focus trap, initial focus, and focus return come from the browser — not hand-built. |
| Dialog dismissal | Escape (native, fires the `close` event), an explicit close button (`IconButton`, reused), and backdrop click (`event.target === dialogRef.current` check — the one piece of custom JS this component needs) |
| Accordion implementation | **Multi-open, native `<details>`/`<summary>`.** Each item is independent; no open/close coordination state. `defaultOpenIds` sets the *initial* `open` attribute only — subsequent toggles are pure DOM, not routed through React state |
| Tooltip trigger | Hover **and** focus (not click) |
| Tooltip dismissal (WCAG 1.4.13) | Escape key, pointer leaving both trigger and tooltip, or blur — **no** auto-hide timeout while hovered/focused |
| Tooltip positioning | **Fixed, CSS-only** (`position: absolute`, always above the trigger). No flip/shift/viewport-collision logic — can overflow at the very top of the viewport, accepted tradeoff |
| Toast architecture | **`ToastProvider` + `useToast()` hook**, the generator's first non-presentational component. Requires the `ComponentFiles.indexExports` addition (§2, §7) |
| Toast auto-dismiss | Default 5000ms, **pauses on hover or focus** (WCAG 2.2.1 Timing Adjustable — a toast that vanishes while a user is still reading or an AT user is still on it is an access failure, not just a UX nicety) |
| Toast live-region strategy | Each toast is its own `role="status"` / `role="alert"` element (tone-driven, reusing Alert's existing logic) at mount time — **not** a single persistent live region with text diffing, which has well-known cross-browser announcement-timing bugs |
| Cross-cutting WCAG gaps in the *existing* 11 components (color-only signaling, target size, reduced-motion, fixed-px font sizes, autocomplete) | **Deferred again**, out of scope for this release — see §9. This release is the four composite components only |

## 4. Workstream A — `Accordion`

**File:** `src/generator/templates.ts` — add `accordionTemplate()`, add it
to `allTemplates()`. Simplest of the four (no custom keyboard code, no
state) — implement first to bank a quick win before Toast's bigger lift.

**API:**
```ts
export interface AccordionItem {
  id: string;
  summary: string;
  content: React.ReactNode;
}
export interface AccordionProps {
  items: AccordionItem[];
  /** Which items start expanded. Sets the initial `open` attribute only. */
  defaultOpenIds?: string[];
}
```

**Markup:** one `<details>` per item (`open={defaultOpenIds?.includes(item.id)}`
on first render only — no `onToggle` wiring back into React state, per the
locked decision), each with a `<summary>` containing `item.summary`, and a
content `<div>` inside. No `role`/`aria-*` needed beyond what `<details>`/
`<summary>` already expose natively.

**CSS:** `.ds-accordion`, `.ds-accordion__item` (border-bottom), 
`.ds-accordion__summary` (join the `:focus-visible` selector list, cursor
pointer, a `::marker` or CSS triangle for the expand/collapse indicator),
`.ds-accordion__content` (padding).

**Tests:**
- Shipped axe test: render with one item pre-opened, one closed — assert
  no violations in that mixed state.
- Shipped test: `@testing-library/user-event` click on a closed item's
  summary, assert its `<details>` now has the `open` attribute; assert a
  *different* item that started open is still open (proves independence,
  not just that toggling works).
- `test/generate.test.ts` (this repo): assert generated `Accordion.tsx`
  contains `<details`, `<summary`, and does **not** contain `role="region"` or
  a hand-rolled `aria-expanded` (proving it's actually using the native
  element, not silently reimplementing ARIA disclosure by hand).

## 5. Workstream B — `Tooltip`

**File:** `src/generator/templates.ts` — add `tooltipTemplate()`, add it to
`allTemplates()`.

**API:**
```ts
export interface TooltipProps {
  /** The tooltip's text — also becomes the trigger's accessible description. */
  content: string;
  /** The trigger element. Must accept a ref and spread props (a DOM element
   *  or a component like Button/IconButton that forwards both). */
  children: React.ReactElement;
}
```

**Behavior:** `Tooltip` clones `children` via `React.cloneElement` to attach
`aria-describedby={id}`, `onMouseEnter`/`onMouseLeave`, `onFocus`/`onBlur`,
and a ref — no extra wrapper element around the trigger itself (avoids
disturbing the consumer's layout). Visibility state tracks hover-or-focus
on *either* the trigger or the tooltip bubble (so moving the pointer from
trigger to tooltip doesn't hide it — the "hoverable" requirement).
`onKeyDown` on the trigger closes on Escape without blurring it (the
"dismissible" requirement). No `setTimeout`-based hide while hovered or
focused (the "persistent" requirement) — WCAG 1.4.13 is a hard requirement
here, not a nice-to-have, since it's the cited reason this component made
the roadmap.

**Markup:** `role="tooltip"` on the bubble, `id={id}` matching the
trigger's `aria-describedby`, absolutely positioned (relative to a
non-visual wrapping `<span style={{ position: 'relative', display:
'inline-block' }}>` around trigger + bubble — the one wrapper element that
*is* needed, but it's a plain span with no semantics of its own).

**CSS:** `.ds-tooltip` (background `--ds-color-text`, text
`--ds-color-background` — an intentional inversion of an already
contrast-checked pair, so no new contrast validation is needed; contrast
is symmetric regardless of which side is foreground vs. background),
positioned `top: -100%` / equivalent fixed offset above the trigger, small
arrow via a pseudo-element (optional, CSS-only).

**Tests:**
- Shipped axe test: render the tooltip in its visible state (bypass the
  hover logic by rendering with an internal `forceVisible` test-only prop,
  **or** simpler — just axe-check the trigger+content in the DOM
  regardless of visibility, since axe doesn't require pixel visibility to
  check `aria-describedby` wiring and role correctness).
- Shipped test: `user-event.hover(trigger)`, assert the tooltip becomes
  visible and `trigger` has `aria-describedby` pointing at it; `user-event.unhover`,
  assert it hides; focus + Escape, assert it hides without moving focus
  off the trigger.

## 6. Workstream C — `Dialog`

**File:** `src/generator/templates.ts` — add `dialogTemplate()`, add it to
`allTemplates()`. Implement after Accordion and Tooltip so the "shipped
test can't cover the real behavior" caveat (§2) is documented once the
easier wins are already in and the pattern for composite components is
warmed up.

**API:**
```ts
export interface DialogHandle {
  open: () => void;
  close: () => void;
}
export interface DialogProps {
  /** Rendered as the dialog's Heading (level 2) and wired to aria-labelledby. */
  title: string;
  children: React.ReactNode;
  /** Fires on any dismissal path: Escape, backdrop click, or the close button. */
  onClose?: () => void;
}
export const Dialog: React.ForwardRefExoticComponent<
  DialogProps & React.RefAttributes<DialogHandle>
>;
```

**Behavior:** `useImperativeHandle` exposes `{ open: () => dialogRef.current?.showModal(),
close: () => dialogRef.current?.close() }`. The native `close` event
(fires on Escape *and* on `.close()`) calls `onClose`. Backdrop dismissal:
an `onClick` on the `<dialog>` element itself checks
`event.target === dialogRef.current` (a click that lands on the dialog
element and not any of its content, since content clicks stop at their own
element) and calls `.close()`. Initial focus and focus-return on close are
native browser behavior — no code needed.

**Markup:** `<dialog ref={dialogRef} onClose={...} onClick={...}>` containing
a header (`Heading level={2} id={titleId}`, `IconButton icon={xIcon}
aria-label="Close" onClick={() => dialogRef.current?.close()}`) and the
`children` body. `aria-labelledby={titleId}` on the `<dialog>` itself
(native modal semantics — `role="dialog"` and `aria-modal="true"` — are
implicit once opened via `showModal()`, not written by hand).

**CSS:** `.ds-dialog` (surface background, radius, padding, max-width,
centered via the browser's native `<dialog>` centering), `.ds-dialog::backdrop`
(fixed `rgba(0, 0, 0, 0.5)` — not token-driven or contrast-checked; it's a
decorative scrim, not text), `.ds-dialog__header` (flex row, title + close
button), `.ds-dialog__body`.

**Tests:**
- Shipped axe test: render `<Dialog open>` — wait, **no** `open` prop
  exists (imperative API only per the locked decision) — so: render the
  `Dialog` and directly set the underlying DOM node's `open` attribute in
  the test (`container.querySelector('dialog')!.setAttribute('open', '')`)
  to reach the visual open state, then axe-check markup/roles/labelling.
  **Explicitly does not** exercise `showModal()`/focus-trap/focus-return —
  jsdom can't (§2's correction). Say so in a code comment in the shipped
  test itself, not just this spec, so a future contributor doesn't assume
  more coverage than exists.
- `Dialog.docs.md` (via `fallbackDocs`/AI docs, `src/ai/docs.ts`) should
  note the same limitation for consumers: automated tests here cover
  markup, not modal behavior — recommend manual keyboard testing.
- `test/generate.test.ts` (this repo): assert generated `Dialog.tsx`
  contains `<dialog`, `showModal`, `aria-labelledby`.

## 7. Workstream D — `Toast`

**File:** `src/generator/templates.ts` — add `toastTemplate()`, add it to
`allTemplates()`. Last, since it's the biggest lift and benefits from
Dialog/Accordion/Tooltip having already exercised the "multi-file,
multi-test composite component" conventions.

**API:**
```ts
export type ToastTone = 'info' | 'success' | 'warning' | 'danger';
export interface ToastOptions {
  message: string;
  tone?: ToastTone;
  /** ms before auto-dismiss. 0 disables auto-dismiss entirely. Default 5000. */
  duration?: number;
}
export function ToastProvider(props: { children: React.ReactNode }): React.ReactElement;
export function useToast(): {
  toast: (options: ToastOptions) => string; // returns the toast's id
  dismiss: (id: string) => void;
};
```

**Behavior:** `ToastProvider` holds `{ id, message, tone, duration }[]` in
state and renders a fixed-position stack (`.ds-toast-stack`, e.g.
bottom-right). Each toast schedules its own `setTimeout` for
`duration` (skipped when `duration === 0`), **cleared on mouseenter/focus
and rescheduled on mouseleave/blur** (the pause-on-hover requirement —
implemented per-toast, not globally, so hovering one toast doesn't pause
others). `useToast()` reads the context `ToastProvider` establishes and
throws a clear error if called outside one (consistent with how every
other hook-based library fails loudly rather than silently no-op-ing).

**Markup:** each toast is `role={tone === 'danger' ? 'alert' : 'status'}`
(the exact `Alert` logic, reused) with the message and a close
`IconButton` (`aria-label="Dismiss notification"`). No separate
`aria-live` region wrapper — the role itself is the live-region
mechanism, applied fresh per toast at mount (avoids the diffing bugs a
shared persistent region has).

**CSS:** `.ds-toast-stack` (`position: fixed`, stacked with `gap`),
`.ds-toast` (tone-colored left border matching `Alert`'s existing
`--ds-alert--{tone}` border-left convention, surface background, radius,
padding, shadow).

**Tests:**
- Shipped axe test: render `ToastProvider` wrapping a test harness
  component that calls `useToast().toast(...)` on mount for each tone,
  assert no violations across all four.
- Shipped test: `vi.useFakeTimers()` — trigger a toast with a short
  duration, advance timers, assert it's removed; trigger another, hover
  it, advance past its duration, assert it's **still present** (pause-on-hover
  proof), then unhover and advance again, assert it's now removed.
- `test/generate.test.ts` (this repo): assert generated `Toast.tsx`
  exports `ToastProvider` and `useToast` (not a default `Toast`/`ToastProps`
  pair), and that `src/index.ts` in a real `generate()` run correctly
  emits `export { ToastProvider, useToast, type ToastOptions } from
  './Toast/Toast';` instead of the standard pattern — proves the
  `indexExports` override (§7 cross-cutting) actually works end-to-end.

## 8. Cross-cutting changes

- `src/generator/templates.ts` → `ComponentFiles` interface: add optional
  `indexExports?: string`. When set, `renderIndexTs()` (§ below) emits it
  verbatim instead of the default `export { Name, type NameProps }` line.
  Every existing template (Button through Heading) is unaffected — they
  simply don't set the field.
- `src/generator/scaffold.ts` → `renderIndexTs()`: change the `.map()` to
  `c.indexExports ?? \`export { ${c.name}, type ${c.name}Props } from
  './${c.name}/${c.name}';\``.
- `toastTemplate()` sets `indexExports: "export { ToastProvider, useToast,
  type ToastOptions } from './Toast/Toast';"`.
- `test/generate.test.ts`: the existing
  `expect(result.components).toEqual([...])` assertion gets four more
  entries. `result.components` is derived from `ComponentFiles.name`
  (`'Toast'`), which is used for the *directory/file* name
  (`src/Toast/Toast.tsx`) regardless of what `indexExports` actually
  exports — no change needed to how `generate()` itself writes files, only
  to `renderIndexTs()`.
- No changes needed to `src/tokens/schema.ts` or `resolveTokens()` — none
  of the four components introduce a new color pair outside what's already
  contrast-checked (Dialog's backdrop is decorative and explicitly not
  contrast-checked, matching precedent; Tooltip's inverted text/background
  reuses an existing checked pair).
- No changes needed to `src/ai/docs.ts` — doc generation is generic over
  any `ComponentFiles` entry regardless of what it exports (verified: no
  component names are hardcoded there, same as noted in the v2.2.0 spec).

## 9. Out of scope for v2.5.0

- The five cross-cutting WCAG gaps in the *existing* 11-component set
  (1.4.1 color-only signaling, 2.5.8 target size, 2.3.3 reduced-motion,
  1.4.4/1.4.10 fixed-px font sizes, 1.3.5 autocomplete) — deferred again,
  per the locked decision in §3. Still tracked, still the right list to
  start from next time.
- Dialog focus-trap/initial-focus/focus-return **automated** test
  coverage — not achievable with this project's jsdom version (§2). Real
  verification is manual/browser-based only. Revisit if/when jsdom adds
  `showModal()` support, or if Storybook `play` functions (running in a
  real browser via Chromatic) get introduced as new generator
  infrastructure — that would be a bigger, separate infrastructure change,
  not part of this release.
- Tooltip smart positioning (flip/shift to avoid viewport overflow) — per
  the locked decision, fixed placement only.
- A "toast queue size limit" or stacking-order animation — the stack just
  grows; no max-visible-count or enter/exit transition beyond what CSS
  gives for free.
- Nested/stacked dialogs (a dialog opening another dialog) — single-level
  only. The native `<dialog>` element supports nesting, but the initial
  `Dialog` component doesn't add anything special for it.
- Any other WAI-ARIA composite pattern (Menu, Combobox, Listbox, etc.) —
  each is its own release-sized effort, same note as the v2.2.0 spec.
- Dark-theme variants — still blocked on the same single-theme limitation
  noted in v2.1.0 and v2.2.0.

## 11. Versioning note

Same as v2.1.0/v2.2.0 (`.releaserc.json`, semantic-release + conventional
commits): land as `feat:` commit(s) on `main`. **Unlike v2.2.0, strongly
prefer landing this as a small number of PRs merged close together (or one
combined PR)** — v2.2.0's three independently-branched PRs each triggered
their own semantic-release minor bump (`2.2.0`/`2.3.0`/`2.4.0` for what was
meant to be one `2.2.0` release), and the same four-separate-PRs approach
here would consume versions `2.5.0` through `2.8.0` for one logical
release. Do not hand-tag any version.
