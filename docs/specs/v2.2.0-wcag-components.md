# v2.2.0 — Tabs, Heading, and an Accessible-Name Gate

**Status:** specified, not yet implemented
**Scope:** this repo only. Nothing here touches CI/branch-protection infrastructure
(that shipped in v2.1.0) — it's three additions to the generated component set
and the fail-closed accessibility model that set is built on.

This document is self-contained: it assumes only the current state of
`@benjaminmcosker/design-system-generator` (post v2.1.0) and needs no other
context to implement.

---

## 1. Goal

Extend the generated component library with the three highest-value gaps left
after v2.1.0's contrast gate:

1. **Tabs** — the WAI-ARIA Authoring Practices tabs pattern (WCAG 2.1.1
   Keyboard, 2.4.3 Focus Order, 4.1.2 Name/Role/Value). None of the current 8
   components are a composite widget with roving tabindex and arrow-key
   navigation; Tabs is the canonical hard case for keyboard accessibility and
   is missing entirely.
2. **Heading** — a semantic `<h1>`–`<h6>` primitive (WCAG 1.3.1 Info and
   Relationships, 2.4.6 Headings and Labels). Nothing today emits a heading
   element; consumers are left to hand-roll `<h1>`–`<h6>` with no token-driven
   sizing and no structural safety net.
3. **Accessible names, made hard to omit** — a new `IconButton` (icon-only,
   no visible text) whose accessible name is enforced both at the type level
   and at runtime, plus a test proving the enforcement actually catches a
   violation, mirroring the pass/fail fixtures matrix that proved the
   contrast gate in v2.1.0.

## 2. What already exists (do not rebuild)

- **Focus visibility (WCAG 2.4.7):** already solved generically.
  `src/generator/css.ts` puts `:focus-visible` rings (token-driven color,
  already contrast-checked at ≥3:1 via `resolveTokens()`) on every existing
  interactive class. Tabs' new interactive elements just need to join that
  same selector list — no new mechanism.
- **Accessible names for existing components:** already fully enforced by
  the type system, not by convention. `TextField`, `Checkbox`, `Switch`, and
  `Select` all require `label: string`; `RadioGroup` requires `legend:
  string`; `Button` requires `children`. There is currently no way to emit
  an unlabeled interactive control from the existing 8 templates — the gap
  only exists once an icon-only control is introduced, which is exactly what
  Workstream C adds.
- **Native keyboard semantics:** `RadioGroup`, `Switch`, and `Select` all
  lean on native element behavior for keyboard support (see the doc-comments
  in `src/generator/templates.ts` above each). Tabs has no native element to
  lean on — arrow-key roving tabindex has to be hand-built, which is exactly
  why it's the one component in this release that needs real interaction
  code, not just markup.
- **`expectNoAxeViolations()`** (`src/generator/scaffold.ts` →
  `renderAxeHelper()`) disables only the `color-contrast` rule (contrast is
  checked from token values instead, per v2.1.0). Every other default
  axe-core rule is already active on every generated test, including
  `heading-order` and `button-name` — Workstreams B and C don't need any new
  axe configuration, only tests that actually exercise those rules.

### Corrections to an assumption from scoping this release

Accessible-name enforcement **cannot** work the way the contrast gate does.
`resolveTokens()` can reject bad contrast before generation because contrast
is fully determined by token values the generator already has in hand. An
accessible name on `IconButton` depends on how a *future consumer* calls the
component in *their* app — that JSX doesn't exist yet when `dsg generate`
runs, so there is nothing to statically check at generation time.

The practical equivalent, and what Workstream C actually builds:
- **Compile-time:** `aria-label` is a required (non-optional) prop on
  `IconButtonProps`, so TypeScript rejects a call site that omits it
  entirely — this is arguably stronger than a generation-time check, since
  it fires in the consumer's editor before they even run anything.
  TypeScript can't check the *content* of a string, though, so:
- **Runtime (dev-mode only):** `IconButton` logs a console error if
  `aria-label` is present but empty/whitespace, the one case the type system
  can't catch.
- **Test-proven:** a test (in this repo, not shipped to consumers) renders
  `IconButton` with an empty `aria-label` (bypassing the type check
  deliberately, the same way the contrast fixtures deliberately fail) and
  asserts `expectNoAxeViolations()` throws — proving axe-core's `button-name`
  rule is the actual backstop, not just the dev-mode console message.

## 3. Decisions (locked)

| Decision | Choice |
| --- | --- |
| New components this release | `Tabs`, `Heading`, `IconButton` |
| Tabs activation model | **Automatic activation** (arrow keys move focus *and* selection together) — the simpler of the two APG-sanctioned patterns, and sufficient for uses where switching tabs is cheap |
| Tabs keyboard support | ArrowLeft/ArrowRight move + select (wrapping at the ends), Home/End jump to first/last, only the active tab is in the Tab order (roving `tabIndex`) |
| Heading sizing | Extend the existing 4-step font-size ladder (`sm/base/lg/xl`) to 6 steps (`sm/base/lg/xl/2xl/3xl`) so every `h1`–`h6` has a distinct, token-driven size |
| IconButton accessible name | Required (non-optional) `aria-label` prop at the type level + dev-mode runtime check for empty strings + axe-core `button-name` as the proven backstop |
| New devDependency for generated systems | `@testing-library/user-event` — needed to test Tabs' arrow-key interaction; existing devDeps only cover render + axe, not simulated keyboard input |
| Where "prove the gate has teeth" tests live | **This repo only** (`test/`), not shipped into generated systems — a generated axe test that's designed to fail would break every consumer's `npm test` |

## 4. Workstream A — `Tabs`

**File:** `src/generator/templates.ts` — add `tabsTemplate()`, add it to the
`allTemplates()` array.

**API:**
```ts
export interface TabItem {
  id: string;
  label: string;
  content: React.ReactNode;
}
export interface TabsProps {
  /** Accessible name for the tablist itself (aria-label). */
  label: string;
  items: TabItem[];
  activeId?: string;
  defaultActiveId?: string;
  onChange?: (id: string) => void;
}
```

**Markup / ARIA (WAI-ARIA APG tabs pattern):**
- Container: `role="tablist"` `aria-label={label}`.
- Each tab: `role="tab"`, `id={base-tab-${item.id}}`,
  `aria-controls={base-panel-${item.id}}`, `aria-selected`, roving
  `tabIndex` (`0` for the active tab, `-1` for the rest).
- Each panel: `role="tabpanel"`, `id={base-panel-${item.id}}`,
  `aria-labelledby={base-tab-${item.id}}`, `tabIndex={0}` (so panel content
  with no focusable children is still keyboard-reachable), `hidden` when
  inactive.
- `base` id from `React.useId()`.
- `onKeyDown` on the tablist handles ArrowLeft/ArrowRight (wrap around),
  Home/End, moves both the selected id and DOM focus (`.focus()` on the
  newly active tab button ref).

**CSS:** `src/generator/css.ts` — add `.ds-tabs`, `.ds-tabs__list`,
`.ds-tabs__tab` (join the existing `:focus-visible` selector list),
`.ds-tabs__tab[aria-selected='true']` (underline/indicator using
`--ds-color-primary`, which is already checked as a ≥3:1 UI boundary color by
`resolveTokens()` — no new contrast pair needed), `.ds-tabs__panel`.

**Tests:**
- `src/generator/templates.ts` axe test (shipped): render 3 tabs, assert no
  violations in the default state.
- `src/generator/templates.ts` axe test (shipped): using
  `@testing-library/user-event`, press ArrowRight twice and assert the third
  tab is now selected and focused, then assert no axe violations.
- `test/generate.test.ts` (this repo): assert the generated `Tabs.tsx`
  contains `role="tablist"`, `aria-selected`, and `role="tabpanel"`.

## 5. Workstream B — `Heading`

**File:** `src/generator/templates.ts` — add `headingTemplate()`, add it to
`allTemplates()`.

**API:**
```ts
export interface HeadingProps extends React.HTMLAttributes<HTMLHeadingElement> {
  level: 1 | 2 | 3 | 4 | 5 | 6;
}
```
Renders the matching native tag (`h1`…`h6`) via
`React.createElement('h' + level, ...)` — never a styled `div` pretending to
be a heading.

**CSS:** `src/generator/css.ts` →
- `renderTokensCss()`: extend `sizes` from `['sm', 'base', 'lg', 'xl']` to
  `['sm', 'base', 'lg', 'xl', '2xl', '3xl']` (same `scale ** (i - 1)`
  formula, just two more steps), emitting `--ds-font-size-2xl` /
  `--ds-font-size-3xl`.
- `renderStylesCss()`: `.ds-heading--1` → `3xl`, `--2` → `2xl`, `--3` → `xl`,
  `--4` → `lg`, `--5` → `base`, `--6` → `sm`, color from
  `--ds-color-text` (already checked at ≥4.5:1 against both background and
  surface).

**Tests:**
- Shipped axe test: render `<Heading level={1}>`…`<Heading level={6}>` each
  in isolation — proves each level itself is accessible.
- Shipped axe test: render a **correctly nested** composition (`level=1` →
  `level=2` → `level=3`) — exercises `heading-order`, which is already
  active by default (see §2), against real structure instead of isolated
  elements.
- **This repo only** (`test/heading-order.test.ts`): render a
  **deliberately skipped** composition (`level=1` → `level=3`, no `level=2`)
  and assert `expectNoAxeViolations()` throws — proves `heading-order`
  actually fires, the same "prove the gate has teeth" pattern as the
  contrast fixtures.

## 6. Workstream C — `IconButton` + the accessible-name gate

**File:** `src/generator/templates.ts` — add `iconButtonTemplate()`, add it
to `allTemplates()`.

**API:**
```ts
export interface IconButtonProps
  extends Omit<React.ButtonHTMLAttributes<HTMLButtonElement>, 'children'> {
  icon: React.ReactNode;
  /** Required — IconButton has no visible text, so this is its only name. */
  'aria-label': string;
  variant?: 'primary' | 'secondary' | 'danger';
  size?: 'sm' | 'md' | 'lg';
}
```
- `aria-label` is a required prop (not `?:`), so omitting it is a
  compile-time TypeScript error at the consumer's call site.
- In dev mode (`process.env.NODE_ENV !== 'production'`), log
  `console.error` if `aria-label.trim() === ''`.
- Visually: reuses the existing `.ds-button` classes/variants/sizes so it's
  styled identically to `Button`, just icon-only and square.

**Tests:**
- Shipped axe test: render with a valid `aria-label`, assert no violations.
- **This repo only** (`test/icon-button-name.test.ts`): render with
  `aria-label=""` (cast past the type check, mirroring how the contrast
  fail-fixtures are deliberately invalid) and assert
  `expectNoAxeViolations()` throws via axe-core's `button-name` rule — the
  actual proof that an unlabeled `IconButton` cannot ship silently.

## 8. Suggested implementation order

Simplest and most isolated first, to de-risk the one component with real
interaction logic:

1. **Heading** — no new state, no new interaction, just markup + CSS ladder.
2. **IconButton** — small, but establishes the "type-level + runtime +
   axe-proven" accessible-name pattern that's the point of Workstream C.
3. **Tabs** — the only component with hand-built keyboard handling; benefits
   from the other two already being in and the test conventions settled.

Each can land as its own PR against this spec, or as one combined PR — no
sequencing dependency between them at the code level.

## 9. Out of scope for v2.2.0

- Enforcing document-level heading order *across an entire consumer app* —
  `Heading` gives consumers a correct primitive and axe-core catches skips
  *within a rendered tree*, but the generator has no visibility into how
  consumers compose pages, so app-wide heading structure stays a consumer
  responsibility.
- A "manual activation" Tabs variant (Enter/Space to activate after arrow
  focus) — automatic activation only, per §3.
- Vertical/orientation-aware Tabs (Up/Down instead of Left/Right) — v2.2.0
  ships horizontal only.
- Any other WAI-ARIA composite patterns (Menu, Combobox, Dialog, etc.) —
  each is its own release-sized effort.
- Dark-theme variants of the new components — still blocked on the same
  single-theme limitation noted in the v2.1.0 spec.
