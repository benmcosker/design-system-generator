# v2.9.0 — Dark mode, `'use client'`, line-height, and rem spacing

**Status:** specified, not yet implemented
**Scope:** this repo only. One headline feature (dark mode, both targets) plus three small
generator hardening items. No new components. Post v2.8.0: 18 components, two targets.

This document is self-contained: it assumes only the current state of
`@benjaminmcosker/design-system-generator` and needs no other context to implement.

Tracks backlog issues #28 (dark mode), #29 (`'use client'`), #30 (line-height) and #31
(rem tokens). Where this spec deliberately departs from an issue's text, §3 and §10 say so.

**Motivating reality:** the generator's pitch is "it refuses to emit an inaccessible
palette", but it can only describe *one* palette. Teams with a dark theme either skip the
tool for it or ship an unchecked dark palette, which is exactly the failure the contrast
gate exists to prevent. Dark mode is the longest-deferred item in the project (v2.1.0,
v2.2.0, v2.6.0, v2.7.0 specs all punted it).

## 2. What already exists (do not rebuild)

- **Token schema** (`src/tokens/schema.ts`): `colors` (8 required + optional palette and
  label-override slots), `typography`, `spacing.unitPx`, `radius.{sm,md,lg}` (free-form CSS
  length strings), `focus`. `ResolvedTokens.computed` holds the derived values.
- **The contrast gate** (`resolveTokens()` in `src/tokens/parse.ts`): builds a list of
  `ContrastCheck` pairs from `colors` + `computed`, adds shadcn-only pairs when
  `target === 'shadcn'`, throws `AccessibilityError` listing every failing pair.
  `bestTextOn()` picks `#111827` or `#ffffff`; `mixHex()`/`firstMixMeeting()` derive
  `border`/`input`.
- **Emitters:** `renderTokensCss()` and `renderStylesCss()` (`src/generator/css.ts`),
  `renderShadcnThemeCss()` / `shadcnRootVars()` / `shadcnThemeVars()` /
  `renderShadcnRegistryItem()` (`src/generator/shadcn.ts`).
- **Drift check:** `dsg check <tokens> --theme <file>` regenerates the shadcn theme and
  diffs it (`src/cli.ts`, `src/diff.ts`). It compares full file content, so adding a
  dark block to the generated theme is automatically covered, with no new check code.
- **`remFromPx()`** (`css.ts`): the px→rem converter used for the font ladder
  (`px / 16`, trimmed). Reused by workstream D.
- **Touch targets / reduced motion (v2.7.0):** all 24px minimums are in `px` on purpose
  (SC 2.5.8 is defined in CSS px); they stay px. The `prefers-reduced-motion` block is
  untouched.
- **`ComponentFiles`** (`src/generator/templates.ts`) and the `HEADER` constant that begins
  every generated file; `ComponentFiles.indexExports` is the precedent for an optional
  per-component field.
- **Fixtures matrix** (`test/fixtures/contrast`, `test/fixtures/shadcn`) and
  `test/contrast-fixtures.test.ts`: pass/fail token files run through the gate in CI.
- **Chromatic + a11y addon:** the generated Storybook runs `a11y: { test: 'error' }` and
  CI publishes to Chromatic.

### Corrections to earlier assumptions

**Accordion does not need `'use client'`.** The v2.6.0 spec (§8) and issue #29 list
Accordion, but it is native `<details>`/`<summary>` with no hooks and no event handlers
(v2.5.0 §3: "no open/close coordination state"). Verified against the generated source:
the components that call client-only hooks or attach handlers are **Tabs, Tooltip,
Dialog, Toast, Listbox, Menu, Combobox, and RadioGroup**. RadioGroup is the one nobody
listed: it builds an inline `onChange` handler. Button, IconButton, TextField, Select,
Checkbox, Switch, Badge, Alert, Heading and Accordion need no directive (they only
forward consumer props or render static markup). §5 detects this by pattern, not by a
hand-kept list, so it can't drift.

**axe-core in jsdom cannot verify dark-mode contrast.** The generated tests import
`../styles.css`, but jsdom does not resolve `var(--ds-*)` custom properties through
imported stylesheets reliably enough for axe's `color-contrast` rule, and there is no
`prefers-color-scheme` to toggle. The authoritative dark contrast check is the **token
gate**; the real-browser backstop is the Storybook a11y addon (which does compute
colors) running stories under the dark theme. Say so plainly in the generated docs rather
than implying jsdom covers it.

## 3. Decisions (locked)

| Decision | Choice |
| --- | --- |
| Dark schema shape | `modes.dark.colors`, **same key set as `colors`**. The 8 required colors are **required** in dark; optional slots (`secondary`, `accent`, `muted`, `border`, `input`, `chart`, `on*`) are optional and default *from the dark values* exactly as light defaults from light |
| Auto-deriving a dark palette | **Out of scope.** Inverting a brand palette is a design decision; the generator validates a dark palette, it doesn't invent one |
| Backward compatibility | No `modes` key → output is **byte-identical** to v2.8.0 for React and shadcn (asserted by test, same technique as v2.6.0's "byte-identical to v2.5.0") |
| Non-color tokens per mode | Not themable. `typography`, `spacing`, `radius` are shared; `focus.ringWidthPx` shared; `focus.ringColor` may be overridden per mode via `modes.dark.focusRingColor`, defaulting to the dark `primary` |
| Contrast gate | Every pair the light palette is checked on is checked on the dark palette with **identical thresholds**; failures are reported with a `[dark]` prefix on the pair name; **both modes are checked in one pass** so a user sees all failures at once |
| React target selection | `@media (prefers-color-scheme: dark)` applies dark values to `:root:not([data-theme='light'])`, and `:root[data-theme='dark']` forces dark. `color-scheme: light dark` on `:root` (and `light`/`dark` on the forced selectors) so native controls and scrollbars follow |
| shadcn target selection | A `.dark { … }` block (shadcn's own convention) **plus** the `@custom-variant dark (&:is(.dark *));` line Tailwind v4 needs for `dark:` utilities; registry item gains `cssVars.dark` |
| Why two mechanisms | `data-theme` for the React target and `.dark` for shadcn is deliberate: each follows its ecosystem's convention, and a consumer of one never sees the other's |
| Decorative colors | The Dialog backdrop `rgba(0,0,0,.5)` and the `box-shadow` values stay literal (not token-driven, not contrast-checked: decorative, same as v2.5.0). Known tradeoff: shadows are nearly invisible on dark surfaces; the 1px borders carry the separation, so nothing depends on the shadow |
| `'use client'` | Added to the 8 components in §2 as the **first line of the file, before the `HEADER` comment**; driven by a `ComponentFiles.client?: boolean` field and enforced by a pattern test (§5) |
| `line-height` | New token `typography.lineHeight` (unitless, default `1.5`, range 1.2–2) and `typography.lineHeightTight` (default `1.25`, used by Heading) |
| rem scope | Convert **spacing** and **radius** (px values only; non-px lengths pass through verbatim). **Keep `focus.ringWidthPx`, 1–4px borders and outlines, and the 24px minimums in px**: thin strokes shouldn't grow with text size, and 2.5.8 is px-denominated. This narrows issue #31's "focus-ring width"; see §10 open question |
| Chromatic | Dark and text-spacing snapshots are added via Chromatic `modes`, **only when the token spec defines `modes.dark`**. This multiplies snapshot count (cost noted in §10) |
| Release | One combined PR; manual release via the Release workflow (no auto-publish on merge since v2.8.0) |

## 4. Workstream A — Dark mode

### 4.1 Schema (`src/tokens/schema.ts`)

```yaml
modes:
  dark:
    colors:
      primary: "#60a5fa"
      background: "#0b1220"
      surface: "#111a2e"
      text: "#e5e7eb"
      textMuted: "#a3b0c4"
      danger: "#f87171"
      success: "#4ade80"
      warning: "#fbbf24"
    focusRingColor: "#60a5fa"   # optional, defaults to dark primary
```

Factor the `colors` object into a shared `colorsSchema` used by both `colors` and
`modes.dark.colors` (one definition, so the two can never drift). `modes` is
`.optional()`; `ResolvedTokens` gains `modes?: { dark: ResolvedMode }` where
`ResolvedMode = { colors; computed; focusRingColor }`. The existing top-level
`computed` keeps meaning "light", so no existing consumer changes.

### 4.2 Resolver (`src/tokens/parse.ts`)

Extract the body of `resolveTokens()` into `resolveMode(colors, focusRingOverride, target)
→ { computed, checks }`, called once per mode. `resolveTokens()` concatenates both modes'
checks (dark pair names prefixed `[dark] `), runs `findContrastIssues` once, and throws
one `AccessibilityError` if either mode fails. The light path must produce the same
checks in the same order as today.

Verified starting point for the example spec (passes the full react **and** shadcn gate
with the current resolver; derived values: labels `#111827`, border `#2c323e`, input
`#5c616b`, ring = primary):

| Color | Light (existing) | Dark (proposed) |
| --- | --- | --- |
| background | `#ffffff` | `#0b1220` |
| surface | `#f8fafc` | `#111a2e` |
| text | `#0f172a` | `#e5e7eb` |
| textMuted | `#475569` | `#a3b0c4` |
| primary | `#1d4ed8` | `#60a5fa` |
| danger | `#b91c1c` | `#f87171` |
| success | `#15803d` | `#4ade80` |
| warning | `#b45309` | `#fbbf24` |

### 4.3 React emitter (`renderTokensCss()`)

Factor the color custom properties into a helper returning the color-only lines for a
given resolved mode, emitted three times when `modes.dark` exists:

```css
:root { color-scheme: light dark; /* light colors + all non-color tokens */ }
@media (prefers-color-scheme: dark) {
  :root:not([data-theme='light']) { /* dark color vars only */ }
}
:root[data-theme='light'] { color-scheme: light; }
:root[data-theme='dark'] { color-scheme: dark; /* dark color vars only */ }
```

The dark color list is emitted twice (media query and forced selector). That duplication
is the accepted cost of supporting both OS preference and an explicit toggle without
JavaScript; do not reach for a CSS-in-JS or build-time dedupe. `:root` only gets
`color-scheme: light dark` when dark exists, preserving byte-identical output otherwise.

### 4.4 shadcn emitter (`src/generator/shadcn.ts`)

- `shadcnRootVars()` already takes `ResolvedTokens`; give it a mode parameter (default
  light) so the same function builds the `.dark` block: no second list of variable names.
- `renderShadcnThemeCss()` emits `.dark { … }` after `:root`, and
  `@custom-variant dark (&:is(.dark *));` after the header when dark exists.
- `renderShadcnRegistryItem()` adds `cssVars.dark` from the same function.
- `dsg check --theme` needs no change (§2): the regenerated expected file now contains the
  dark block, so a hand-edited dark value is caught as drift.

### 4.5 Storybook (`renderStorybookPreview()`)

When dark is defined: a `globalTypes.theme` toolbar (`light` / `dark`) with a decorator
setting `document.documentElement.dataset.theme`, plus `parameters.chromatic.modes`
`{ light, dark }` so Chromatic snapshots both. The a11y addon then computes real
colors under the dark theme, which is the real-browser backstop from §2. Preview output
is unchanged when `modes.dark` is absent.

### 4.6 Docs and README

`README.md`: a "Dark mode" section (schema, the two selection mechanisms, "you must supply
the palette; we only validate it"). Generated `README.md` documents `data-theme` usage.
The generated component `.docs.md` fallback gets one line that contrast in dark mode is
enforced at the token level (see §2 correction).

### 4.7 Tests

- `test/contrast-fixtures.test.ts` + `test/fixtures/contrast`: new **pass** fixture with a
  valid dark palette; **fail** fixtures: light passes but dark text on dark background
  fails; dark primary fails the 3:1 UI-boundary check; a failure in *both* modes reports
  both (one error, both `[dark]` and unprefixed pairs listed).
- `test/shadcn.test.ts` (+ snapshot): `.dark` block present, `@custom-variant` present,
  `cssVars.dark` in the registry item, drift check fails on an edited `.dark` value, and
  **no-`modes` output is byte-identical to the v2.8.0 snapshot**.
- `test/generate.test.ts`: `tokens.css` contains the media query, `[data-theme='dark']`
  and `color-scheme`; without `modes` it contains none of them.
- `example/tokens.yaml` gains the dark palette above, so CI generates, installs and tests
  a dark-capable system end to end.

## 5. Workstream B — `'use client'`

- `ComponentFiles` gains `client?: boolean`. The generator (`generate.ts`) prepends
  `'use client';\n` to `src/<Name>/<Name>.tsx` when it is set. It must be the first line,
  before the `HEADER` comment, because Next.js only honors the directive at the top of the
  file, before imports.
- Set it on **Tabs, Tooltip, Dialog, Toast, Listbox, Menu, Combobox, RadioGroup**.
- **Pattern test** in `test/generate.test.ts` (this repo): for every generated component
  file, if it matches `/React\.use(State|Effect|Ref|Reducer|Context|ImperativeHandle|LayoutEffect|Callback|Memo)\b|createContext|\bon[A-Z]\w*=\{/`
  it must start with `'use client';`; if it matches none of those it must **not**. A
  future component that adds a hook fails this test until it opts in; a purely
  presentational one can't get the directive by accident.
- `src/index.ts` (the barrel) needs no directive: the directive lives on the leaf modules.
- No change to Toast's custom `indexExports`.

## 6. Workstream C — line-height

- Schema: `typography.lineHeight` (number, 1.2–2, default `1.5`) and
  `typography.lineHeightTight` (default `1.25`).
- `renderTokensCss()`: `--ds-line-height` and `--ds-line-height-tight`, unitless.
- `renderStylesCss()`: add `line-height: var(--ds-line-height)` to every rule that sets
  `font-family: var(--ds-font-family)`; Heading's rule uses the tight token. No component
  has a fixed text-container `height` (verified: the only `height` declarations are the
  1.5rem/1.25rem switch track and knob, and `max-height` on scrolling lists), so a larger
  line-height can't clip text.
- **WCAG 1.4.12 verification:** add a generated Storybook decorator that injects the
  spec's text-spacing override (line-height 1.5, letter-spacing 0.12em, word-spacing
  0.16em, paragraph spacing 2em, all `!important`) as a Chromatic mode `text-spacing`, so
  clipping or overlap shows up as a visual diff. jsdom can't evaluate this; say so.
- `test/a11y-css.test.ts`: every CSS block containing `font-family` also contains
  `line-height`; the tokens file emits both properties unitless.

## 7. Workstream D — rem spacing and radius

- `--ds-space-N`: emit `remFromPx(step * spacing.unitPx)`.
- `radius.sm|md|lg`: if the value matches `/^\d+(\.\d+)?px$/`, convert with `remFromPx`;
  anything else (`50%`, `0.5rem`, `999px` pill radii authored as such) passes through
  verbatim. `.ds-switch` etc. that use `border-radius: 999px` literally stay literal.
- shadcn: `--spacing` becomes rem (`0.25rem`, matching Tailwind's own default), and
  `--radius`, `--radius-sm|md|lg` follow the same px→rem rule.
- Unchanged on purpose (§3): `focus.ringWidthPx`, 1–4px borders/outlines/outline-offsets,
  and every 24px minimum.
- At the default 16px root, the computed pixel values are identical to today, so the
  visual diff in Chromatic should be **empty at default zoom**; the change only shows when
  the root font size changes. Review the snapshot diff with that expectation: any
  default-size diff is a bug, not churn.
- Tests: update the px pins in `test/a11y-css.test.ts`/shadcn snapshot deliberately;
  add a test that `baseSizePx: 18` still yields `--ds-space-*` relative to the 16px root
  (not to `baseSizePx`), matching how `remFromPx` already treats the font ladder; add a
  non-px radius (`50%`) pass-through case.

## 9. Out of scope for v2.9.0

- Generating or suggesting a dark palette from the light one.
- More than two modes (high-contrast, brand variants). The `modes` key is shaped so a
  `highContrast` mode could be added later without a schema break.
- Per-mode `typography`/`spacing`/`radius`.
- `prefers-contrast` and `forced-colors` handling.
- Making the Dialog backdrop and shadows token-driven.
- Changing the shadcn components themselves, or the `ring-ring/50` opacity caveat.
- 44×44 AAA targets (#32), Badge icons (#33), shadcn OKLCH/Tailwind v3/registry
  (#34–#36), collision positioning (#37), multi-select (#38), submenus (#39).

## 10. Open questions (decide before implementing)

1. **Focus-ring width in rem?** Issue #31 includes it; this spec keeps it in px (§3) so
   thin strokes don't scale. If you want it in rem anyway it is a one-line change plus the
   test pin, and 3px at the default root becomes `0.1875rem`.
2. **Chromatic snapshot cost.** Dark + text-spacing modes roughly triple snapshots per
   story (18 components × stories × 3). If the plan's snapshot quota is tight, limit
   `text-spacing` to a single representative story or drop it to a manual Storybook toggle.
3. **Split the release?** Workstreams B, C, D are independent of A and cheap. If dark mode
   slips, B+C (and D) can ship as 2.9.0 and dark mode as 2.10.0 with no rework.

## 11. Definition of done

- [ ] A token spec with `modes.dark` is validated by the same AA gate; light-only specs
      produce **byte-identical** output to v2.8.0 (React and shadcn), asserted by test.
- [ ] Dark failures are reported with a `[dark]` prefix, together with any light failures
      in a single error.
- [ ] React `tokens.css` emits the media query and `data-theme` selectors with
      `color-scheme`; shadcn `theme.css` emits `.dark` and `@custom-variant dark`;
      the registry item has `cssVars.dark`; `dsg check --theme` catches a hand-edited
      `.dark` value.
- [ ] The 8 components in §2 start with `'use client';`; the pattern test passes in both
      directions; Accordion does not have it.
- [ ] `--ds-line-height` / `--ds-line-height-tight` emitted; every font-setting rule has a
      `line-height`.
- [ ] Spacing and px radii emit in rem; non-px radii pass through; computed px at the
      default root is unchanged (empty Chromatic diff at default zoom).
- [ ] `example/tokens.yaml` includes the dark palette; `dsg generate example/tokens.yaml
      -o generated-ds` followed by `npm test` inside the output passes with 18 components.
- [ ] Generated docs state that dark-mode contrast is enforced at the token level and
      not by jsdom, and that 1.4.12 is verified visually, not by automated test.
- [ ] `npm run typecheck && npm test && npm run build` pass; verified with
      `rm -rf node_modules && npm ci`.

## 12. Versioning note

Same as v2.5.0–v2.8.0 (`.releaserc.json`, semantic-release + conventional commits).
v2.8.0 is the latest release, so one `feat:` commit on `main` yields **2.9.0**. Land as
**one combined PR with a `feat:` title, and merge it with a merge commit (or rewrite the
squash title to `feat:`)**. A squash that keeps this spec's `docs:` title would hide the
`feat:` commits from semantic-release and produce no release, which is what v2.8.0's merge
had to work around. Releases are manual: run the Release workflow from `main` after
merging. Do not hand-tag any version. The spec itself lands as a `docs:` commit.

Suggested implementation order, all in the one PR: **B** (smallest, isolated) → **C** →
**D** (isolate its snapshot churn before dark mode adds more) → **A**.
