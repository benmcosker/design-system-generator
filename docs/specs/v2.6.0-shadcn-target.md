# v2.6.0: shadcn/ui theme target

**Status:** specified, not yet implemented
**Scope:** this repo only. Adds a second output target to `dsg generate`: instead of a
React component library, emit a **shadcn/ui + Tailwind v4 theme** from the same token
spec, behind the same WCAG AA contrast gate. No changes to the existing React target.

This document is self-contained: it assumes only the current state of
`@benjaminmcosker/design-system-generator` (post v2.5.0, 15 components) and needs no
other context to implement.

**Motivating use case:** a Next.js storefront built on shadcn/ui wants its brand
tokens owned by dsg, so every palette change goes through `dsg check`, while the
components come from shadcn.

---

## 1. Goal

Many teams won't adopt a generated component library, but will adopt shadcn/ui,
which is copied into their repo and themed entirely through CSS custom properties.
dsg's two strongest features (one token spec as the source of truth, and
**refusing to emit an inaccessible palette**) are just as valuable there.

1. **`--target shadcn`**: `dsg generate tokens.yaml --target shadcn -o <dir>` writes a
   theme stylesheet that defines every shadcn CSS variable from the token spec, plus
   the Tailwind v4 `@theme inline` block that exposes them as utilities.
2. **Every shadcn color pairing is contrast-checked**, not just the pairs the React
   target uses. shadcn places `muted-foreground` on `muted`, `secondary-foreground` on
   `secondary` and so on; those pairs must pass AA before anything is emitted.
3. **Drift detection**: `dsg check tokens.yaml --theme <file>` fails if a committed
   theme file no longer matches what the tokens would generate. That catches hand-edited
   colors in the consuming repo, which would otherwise bypass the contrast gate.
4. **Registry item**: the same output as a shadcn registry item, so a consumer can
   run `npx shadcn add <url-or-path>` instead of copying CSS by hand.
5. **Label-color overrides (both targets)**: a token file can set the text color used on
   filled colors (e.g. `onPrimary: "#000000"`) instead of accepting the computed one. The
   override is still contrast-checked, so it can only make a palette pass legitimately.

## 2. What already exists (do not rebuild)

- **Token schema** (`src/tokens/schema.ts`): `colors` (primary, background, surface,
  text, textMuted, danger, success, warning), `typography`, `spacing`, `radius`,
  `focus`. Validated with zod.
- **Contrast engine** (`src/tokens/contrast.ts`): `contrastRatio()`, `bestTextOn()`,
  `findContrastIssues()`. `resolveTokens()` in `src/tokens/parse.ts` computes on-colors
  (`onPrimary`, `onDanger`, `onSuccess`, `onWarning`, `focusRingColor`) and throws
  `AccessibilityError` listing every failing pair. The shadcn target reuses all of this.
- **`bestTextOn()` only chooses between `#111827` and `#ffffff`.** A saturated fill can
  fail with both even though another label passes: `#ff0000` gets `#111827` at 4.44:1
  (fails 4.5:1) while `#000000` on it is 5.25:1. Today such a palette can only pass by
  changing the brand color. §4.2 fixes this without changing any existing output.
- **Computed on-colors map directly to shadcn's `-foreground` convention**: shadcn's
  `--primary-foreground` *is* dsg's `onPrimary`.
- **Token CSS emission** (`renderTokensCss()` in `src/generator/css.ts`): already derives
  the font-size ladder (`baseSizePx × scale^n`) and spacing steps. The shadcn target
  reuses the same math so both targets agree on sizes.
- **CLI** (`src/cli.ts`, commander): `generate <tokens> -o <dir> [--ai-docs]` and
  `check <tokens>`. Both gain one option each (§3).
- **CI** (`.github/workflows/ci.yml`): typecheck/test/build, contrast gate over
  `example/tokens.yaml` and the fixtures matrix, and generate-then-axe for the React
  target. A shadcn job is added alongside (§6).

## 3. Decisions (locked)

| Decision | Choice |
| --- | --- |
| CLI shape | `--target <react\|shadcn>` on `generate`, default `react` (today's behavior, byte-for-byte unchanged). |
| Tailwind version | **Tailwind v4 only** (CSS-first `@theme inline`), which is what current shadcn/ui targets. No `tailwind.config.js` output; v3 is out of scope. |
| Color format | Emit **hex**, exactly as written in the token spec. shadcn's variables accept any CSS color, and hex keeps the output diffable against `tokens.yaml`. OKLCH conversion is out of scope. |
| Dark mode | **Single palette → `:root`** this release. A dark-only site simply uses a dark palette. A `.dark` block needs a second validated palette in the schema and is deferred (§8). |
| New tokens | Optional `colors.secondary`, `colors.accent`, `colors.muted`, `colors.border`, `colors.input`, `colors.chart` (array of up to 5). All default from existing tokens, so **every existing token file works unchanged**. |
| Label-color overrides | Optional `colors.onPrimary`, `colors.onDanger`, `colors.onSuccess`, `colors.onWarning` (both targets) and `colors.onSecondary`, `colors.onAccent` (shadcn target). When set, it replaces the `bestTextOn()` result and is checked against the same pairs at the same ratios. When unset, output is exactly today's. See §4.2. |
| New contrast checks | Only run for `--target shadcn`, so existing React-target specs can't start failing. Listed in §4.3. |
| Drift check | `dsg check <tokens> --theme <file>`: regenerate in memory, compare to the file, ignoring the header comment. Exit 1 with a unified diff on mismatch. |
| Output files | `<out>/theme.css`, `<out>/registry-item.json`, `<out>/README.md`. No `package.json`, components or Storybook. |
| `--ai-docs` with `--target shadcn` | Rejected with a clear error (nothing to document). |

## 4. Workstream A: token schema and contrast

### 4.1 Schema additions (`src/tokens/schema.ts`)

All optional; defaults are resolved in `resolveTokens()` so they can depend on other tokens.

| Token | Default |
| --- | --- |
| `colors.secondary` | `colors.surface` |
| `colors.accent` | `colors.surface` |
| `colors.muted` | `colors.surface` |
| `colors.border` | Mix of `colors.text` into `colors.background` at 15%. Decorative, no contrast requirement. |
| `colors.input` | The lightest (on a light background) or darkest (on a dark one) mix of `text` into `background` that reaches **3:1** against `background`. Form-field boundaries fall under WCAG 1.4.11. |
| `colors.chart` | `[primary, success, warning, danger, textMuted]` |

The mixing helper (`mixHex(a, b, t)`) and the "search for the first mix that meets
ratio *r*" helper go in `src/tokens/contrast.ts`, with unit tests.

`ResolvedTokens.computed` gains `onSecondary`, `onAccent` and `onMuted` (via
`bestTextOn()`); the resolved values of every optional color above are stored too.

### 4.2 Label-color overrides (both targets)

| Token (optional, hex) | Replaces | Checked as |
| --- | --- | --- |
| `colors.onPrimary` | `computed.onPrimary` | "label on primary button", 4.5 |
| `colors.onDanger` | `computed.onDanger` | "label on danger button", 4.5 |
| `colors.onSuccess` | `computed.onSuccess` | new "label on success", 4.5, only when set |
| `colors.onWarning` | `computed.onWarning` | new "label on warning", 4.5, only when set |
| `colors.onSecondary` | `computed.onSecondary` | "label on secondary", 4.5 (shadcn target) |
| `colors.onAccent` | `computed.onAccent` | "label on accent", 4.5 (shadcn target) |

- In `resolveTokens()`: `computed.onX = colors.onX ?? bestTextOn(colors.X)`. Nothing
  else changes; every consumer of `computed` (React templates, `renderTokensCss()`, the
  shadcn emitter) picks the override up for free.
- A failing override is reported with the existing message format, naming the override
  (e.g. `label on primary button: #444444 on #ff0000 is 1.9:1 (needs 4.5:1)`), so a user
  can't bypass the gate with a bad value.
- Today no pair checks the computed `onSuccess` / `onWarning`, so their new pairs run only
  when the override is set. That keeps existing specs from gaining new failures.
- `onSecondary` / `onAccent` are accepted but unused by the React target (it has no such
  fills); they are not an error there.
- `bestTextOn()` itself is unchanged, so every existing token file resolves byte-for-byte
  the same.

### 4.3 Contrast pairs for the shadcn target

Checked in addition to today's pairs, only when the target is `shadcn`:

| Pair | Foreground | Background | Required |
| --- | --- | --- | --- |
| label on secondary | `onSecondary` | `secondary` | 4.5 |
| label on accent | `onAccent` | `accent` | 4.5 |
| muted text on muted | `textMuted` | `muted` | 4.5 |
| muted text on surface (card/popover) | `textMuted` | `surface` | 4.5 |
| text on muted | `text` | `muted` | 4.5 |
| input boundary | `input` | `background` | 3 |
| focus ring on surface | `focusRingColor` | `surface` | 3 |
| each chart color | `chart[n]` | `background` | 3 |

`resolveTokens(spec, { target })` takes the target; the React path passes `react` and
runs exactly today's list. Failures use the existing `AccessibilityError` message format.

## 5. Workstream B: the shadcn emitter

New file `src/generator/shadcn.ts` exporting `renderShadcnThemeCss(tokens)`,
`renderShadcnRegistryItem(tokens)` and `renderShadcnReadme(tokens)`.
`generate()` in `src/generator/generate.ts` branches on `options.target`.

### 5.1 Variable mapping (`theme.css`, `:root`)

| shadcn variable | Source |
| --- | --- |
| `--background` / `--foreground` | `background` / `text` |
| `--card`, `--popover` | `surface` |
| `--card-foreground`, `--popover-foreground` | `text` |
| `--primary` / `--primary-foreground` | `primary` / `computed.onPrimary` |
| `--secondary` / `--secondary-foreground` | `secondary` / `computed.onSecondary` |
| `--muted` / `--muted-foreground` | `muted` / `textMuted` |
| `--accent` / `--accent-foreground` | `accent` / `computed.onAccent` |
| `--destructive` / `--destructive-foreground` | `danger` / `computed.onDanger` |
| `--border` | `border` |
| `--input` | `input` |
| `--ring` | `computed.focusRingColor` |
| `--radius` | `radius.md` |
| `--chart-1` … `--chart-5` | `chart[0..4]` |
| `--sidebar`, `--sidebar-foreground`, `--sidebar-primary`, `--sidebar-primary-foreground`, `--sidebar-accent`, `--sidebar-accent-foreground`, `--sidebar-border`, `--sidebar-ring` | `surface`, `text`, `primary`, `onPrimary`, `accent`, `onAccent`, `border`, `focusRingColor` |

Also emitted, for dsg-specific tokens that shadcn has no slot for:
`--success`, `--success-foreground`, `--warning`, `--warning-foreground`.

### 5.2 Tailwind v4 bridge (same file)

```css
@theme inline {
  --color-background: var(--background);
  --color-foreground: var(--foreground);
  /* …one --color-* line per color variable above, incl. success/warning… */
  --radius-sm: <radius.sm>;
  --radius-md: <radius.md>;
  --radius-lg: <radius.lg>;
  --font-sans: <typography.fontFamily>;
  --text-sm: <px>;  /* same ladder as renderTokensCss(): sm, base, lg, xl, 2xl, 3xl */
  --spacing: <spacing.unitPx>px;
}
```

Explicit `--radius-sm|md|lg` values replace shadcn's default `calc(var(--radius) - …)`
derivation so the tokens' radii are used as written.

**Implementation note:** verify the exact variable list against the current shadcn/ui
`globals.css` template (Tailwind v4) when implementing. shadcn has renamed and added
variables before (e.g. the `sidebar-*` set). If upstream drops a variable, still emit
it (harmless); if upstream adds one, add it to the mapping in this release.

### 5.3 File header and drift check

`theme.css` starts with:

```css
/* Generated by design-system-generator (target: shadcn) — do not edit by hand.
   Source: <token file basename> · Regenerate: dsg generate <file> --target shadcn */
```

`dsg check <tokens> --theme <path>` (in `src/cli.ts`):
1. Parse and resolve with `target: 'shadcn'`, so contrast failures still fail first.
2. Render `theme.css` in memory.
3. Compare to `<path>`, ignoring the header comment and normalizing line endings.
4. Match → `✓ <path> matches <tokens>`; exit 0. Mismatch → print a unified diff and
   `Theme file has drifted from tokens; regenerate with …`; exit 1.

This is the command a consuming repo runs in CI.

### 5.4 Registry item (`registry-item.json`)

A shadcn registry item of type `registry:theme` whose `cssVars.theme` holds the Tailwind
bridge values and `cssVars.light` the `:root` values, named `<tokens.name>-theme`.
Consumers install it with `npx shadcn add ./path/registry-item.json` (or a hosted URL).
Verify field names against the current registry-item JSON schema when implementing.

### 5.5 README (`README.md` in the output dir)

- How to install: paste into `app/globals.css` after `@import "tailwindcss";`, **or**
  `npx shadcn add` the registry item.
- The drift-check command for CI.
- **Focus-ring caveat (important).** Current shadcn components draw focus rings at
  reduced opacity (e.g. `focus-visible:ring-ring/50`). At 50% opacity the ring no longer
  has the contrast `dsg check` verified. Tell consumers to change those classes to
  full-opacity `ring-ring` in the components they copy in, or accept the gap knowingly.
  dsg themes colors, not component class names, so it can't fix this itself.
  Confirm the current class names against upstream when implementing.

## 6. Tests and CI

**Unit tests** (`test/shadcn.test.ts`, `test/tokens.test.ts`):
- Defaults: a minimal spec (only `name` + the 8 required colors) resolves every new
  optional color, and the React target's resolved output is unchanged.
- `mixHex` and the "first mix meeting ratio" search: exact values for known inputs, and
  the returned `input` color meets 3:1 on both a light and a dark background.
- Each §4.3 pair can fail, with one fixture per pair (e.g. a pale `muted` making
  `textMuted` on `muted` 3.9:1) and the exact message asserted.
- The React target does **not** run §4.3 pairs: a spec that fails only a shadcn pair
  still passes `dsg check` and `dsg generate` without `--target`.
- `renderShadcnThemeCss` snapshot for `example/tokens.yaml`; every variable in §5.1
  present exactly once.
- `registry-item.json` parses and has the expected `type`, `name` and `cssVars` keys.
- `--ai-docs --target shadcn` errors.
- **Label-color overrides (§4.2), both targets:** a spec with `primary: "#ff0000"` and no
  override fails "label on primary button" at 4.44:1; the same spec with
  `onPrimary: "#000000"` passes, and `--ds-color-on-primary` (React) and
  `--primary-foreground` (shadcn) both emit `#000000`. A failing override (e.g.
  `onPrimary: "#444444"`) is rejected with the override value in the message. A spec with
  no overrides resolves identically to v2.5.0.

**Drift check tests:** matching file → exit 0; one color changed by hand → exit 1 with
the diff; header-only differences ignored; a failing-contrast token file → contrast
error, not a diff.

**Fixtures matrix:** add `test/fixtures/shadcn-pass/*.yaml` and
`test/fixtures/shadcn-fail/*.yaml`, run by `npm run check:fixtures` with
`--target shadcn`. Add a pure-red primary to the existing pass/fail fixtures: without an
override in `fail/`, with `onPrimary: "#000000"` in `pass/`.

**CI** (`.github/workflows/ci.yml`), new job *shadcn theme builds*:
1. `node dist/cli.js generate example/tokens.yaml --target shadcn -o generated-shadcn`
2. `node dist/cli.js check example/tokens.yaml --theme generated-shadcn/theme.css`
3. Compile `theme.css` with Tailwind v4 (`@tailwindcss/cli`, pinned as a devDependency)
   against a tiny HTML fixture using `bg-primary text-primary-foreground rounded-md`, and
   assert those utilities exist in the output, which proves the `@theme inline` bridge works.

## 7. Cross-cutting

- `README.md`: a "Using with shadcn/ui" section with the two commands and the
  focus-ring caveat.
- `example/`: no new token file needed; `example/tokens.yaml` must pass the shadcn pairs
  (adjust defaults, not the example, if it doesn't).
- `src/index.ts`: export `renderShadcnThemeCss` for programmatic use.

## 8. Out of scope for v2.6.0

- **Dark mode / `.dark` block.** Needs a `modes.dark` color set in the schema, with every
  pair checked per mode. Likely v2.7.0.
- Generating or modifying shadcn **components** (including rewriting `ring-ring/50`).
- Tailwind v3 `tailwind.config.js` output.
- OKLCH output.
- Publishing a hosted shadcn registry.
- **`'use client'` directives on the React target's interactive components** (Dialog,
  Toast, Tooltip, Accordion). They're needed for Next.js App Router consumers of the
  React target. Worth doing, but it's a React-target change: track separately.

## 9. Definition of done

- `dsg generate example/tokens.yaml` output is byte-identical to v2.5.0.
- `dsg generate <spec> --target shadcn` emits `theme.css`, `registry-item.json` and
  `README.md`; refuses (exit 1, pair-by-pair message) on any §4.3 failure.
- `dsg check <spec> --theme <file>` passes on a fresh file and fails on a hand-edited one.
- Label-color overrides work on both targets, are contrast-checked, and change nothing when unset.
- Theme compiles with Tailwind v4 in CI and exposes the expected utilities.
- Unit, fixture and CI jobs above all green; README documents shadcn usage and the
  focus-ring caveat.

## 10. Versioning note

New CLI option, new optional tokens, and no change to existing output: a `feat:`
commit, so semantic-release publishes **v2.6.0**. If it lands in several PRs, the first
`feat:` takes 2.6.0 and later ones take 2.7.0+. Title follow-up specs by the version
that actually ships (see the v2.5.0 spec's note).
